# DR-056  候選級 replay：CONTRACT-3 加一欄 group_prototypes ＋ 候選特徵磁碟側倉
date: 2026-09-17    status: ACTIVE
context:   老師 9/17 問 buffer 大小。唯讀稽核（Prompt 24-bis）查出現行 replay 的
           實際資料需求與「|M| = 512 筆壓縮紀錄」的說法不一致：`continual_terms`
           走 `reload_features`，每次 replay 都把該 slide 的**整個特徵檔**讀進來
           （`selector/train.py` 的 `Z, _Z_cand, label = reload_features(...)`），
           再重跑 `assign_groups` 與 `run_rounds`。被記憶庫收過的 slide 聯集
           = 訓練集 100%，特徵庫 3,282 檔、19.55 GiB。entry 本身確實不存 feature
           （CONTRACT-3 成立），但**執行期的資料依賴是整個特徵庫**。

           本卡處理的是：能不能只保留每筆快照的 ≤256 個候選特徵就跑完 replay。
           這是隔離分支 `exp/candidate-replay` 的探針，**不 merge 回 main**。
options:   (a) 維持現狀，在稿件裡改寫 buffer 的口徑，說明執行期需要特徵庫
           (b) replay 只吃候選特徵（≤256 × 512 float32），存磁碟側倉
           (c) 同 (b) 但候選特徵塞進 entry（記憶體常駐）
ruling:    **(b)**，PI 於 Prompt 25 追加裁示兩項：
           (i) group 蒸餾走「快照加存 8 個 group 原型，r_new = F_g(g_stored)，
               與 r_old 同輸入」；CONTRACT-3 的凍結欄位變更**要開 DR 記錄**，
               說明變更理由與影響範圍，不得靜默修改 —— 即本卡。
           (ii) 候選特徵落點走**磁碟側倉**，側倉要能獨立量測大小，回報實測 bytes。

           ## 1. CONTRACT-3 的欄位變更

           schema v2 的六欄（tau, sample_key, r_old[J], cand_idx[≤256],
           s_old[≤256], u_old[≤256]）與 DR-052 加的 `class_mask_old`（bool[J]）
           全部不動。新增第八欄：

               group_prototypes: Optional[torch.Tensor]    # [J, D] = [8, 512]

           **為什麼非加不可**：L_KD 的 group 項是 KL(r_old ‖ r_new)。全 slide
           replay 時 r_new = F_g(全 slide 的原型)，與 r_old 同輸入，KL 量的是
           **F_g 的評分行為漂移**。若候選級 replay 改用候選子集的原型，輸入本身
           就變了，KL 會把「輸入漂移」算進蒸餾損失 —— 步驟 5(a) 的合成實測顯示
           候選子集原型與全 slide 原型的**最大絕對差達 0.735**，不是可忽略的量。
           存下 g_stored 是唯一能讓 group 項維持原義的作法。

           **這一欄是 CONTRACT-3「不存 patch feature」的明文例外**：它是
           特徵空間的向量。代價已量測（第 3 節），只有 `candidate_only` 模式
           會寫入，預設為 `None` → 現行路徑的 entry 內容與 schema v2 完全相同。

           ## 2. 影響範圍（逐項）

           | 元件 | 全 slide replay | 候選級 replay |
           |---|---|---|
           | 讀什麼 | 整個 `.pt` 特徵檔（平均 6.10 MiB） | 側倉一檔（≤512 KiB） |
           | 分組原型 | 全 slide `assign_groups(Z)` | **候選子集** `assign_groups(Z_cand)` |
           | 配額 | Σ b_j = min(B, n) | Σ b_j = min(B, 候選數)；空 group 由 active mask 排除 |
           | L_KD patch 項 | `s_new.index_select(cand_idx)` | **位置對齊**（s_old 的順序就是 cand_idx 的順序） |
           | L_KD group 項 | r_new = F_g(全 slide 原型) | r_new = F_g(**g_stored**) |
           | hinge P_old | `selected_from_entry` 的原 index | 同一批 patch 的**子集內位置** |
           | hinge U_old | 等權池化 | **逐值相同**（同一組 patch、同一種池化） |
           | L_replay | 全 slide 上的 L_diag | 候選子集上的 L_diag |

           patch 評分逐列獨立（F_p 吃單一 patch embedding），所以子集上的 s
           與全 slide 的 `s[cand_idx]` 數學上相同；U_old 亦然。**但** run_rounds
           的分組與配額是集合層級的運算，換了輸入集合就換了結果。

           ⚠️ **因此這不是「同方法換 buffer」，而是換了 replay 的定義。**
           probe 的差值必須照此解讀，**不得寫成無損壓縮**。唯一可稱無損的是
           hinge 的 U_old（第 6 組測試釘住）。

           ## 3. 實測 bytes（本機測量，非估算）

           | 項目 | k = 256 | |M| = 128 | |M| = 512 |
           |---|---|---|---|
           | entry（v2 ＋ C_old） | 6,681 B | 0.82 MiB | 3.26 MiB |
           | entry ＋ g_stored | 23,317 B | 2.85 MiB | 11.39 MiB |
           | 其中 g_stored 一欄 | 16,384 B | 2.00 MiB | 8.00 MiB |
           | 磁碟側倉一筆 | 525,957 B | 64.20 MiB | 256.81 MiB |

           對照：現行 replay 的執行期依賴 = 特徵庫 19.55 GiB（3,282 檔）。
           |M| = 512 的側倉上限 256.81 MiB ≈ **1.28%**。g_stored 讓 entry 大 3.5 倍，
           但絕對量（8 MiB @ |M|=512）相對側倉與特徵庫都可忽略。

           ## 4. 執行期斷言（不是 code review）

           `selector/train.py` 的 `no_feature_files` 以 `sys.addaudithook` 監看
           系統層的 `open` 事件：候選級 replay 的整個區間內，只要有人開啟路徑含
           `feats-l1-s256` 的檔案就拋 RuntimeError。測試以 audit hook 反向觀測，
           確認該區間**只開了側倉那一個檔**。

           ## 5. probe 的判準（PI 於 2026-09-17 凍結，先於看到數字）

           四個 run 同批同機：|M| = 128 × {rfull, r256} × {reverse, forward}，fold 1。

           * class-IL 與 Masked：兩序都**不低於對照組 2 個百分點以上**
           * Forgetting：**不高於對照組 3 個百分點以上**
           * 方向一致性：reverse 與 forward **不得一好一壞**

           結論須註明：fold 1 單折、無變異數，**probe 只能排除崩掉，不能確認有效**。
evidence:  實作與測試在 `exp/candidate-replay`（branch point main `081bdcd`）：
           `selector/memory.py`（欄位 ＋ `cand_store_path` / `save_cand_features` /
           `load_cand_features`）、`selector/train.py`（`FEATURE_DIR_MARK`、
           `no_feature_files`、`_candidate_terms`、`fill_memory` 側倉寫入）、
           `scripts/run_exp2.py --replay-candidate-only`、`configs/pathselect.yaml`
           的 `replay.candidate_only: false`、`tests/test_candidate_replay.py`（8 組）。

           ## 補記 2026-09-17（baseline 對數未逐位元對齊；PI 裁定 A 續行）

           probe 機器（RTX 4090 ＋ AMD EPYC 7702、torch 2.8.0）上以現行路徑重跑
           exp3 的 A5 fold 1，最終 class-IL **0.73538483 vs exp3 的 0.80506508**
           （差 6.97e-2），569 筆中 553 筆 `selected_idx` 不同 —— **未通過**
           DR-055 式的逐位元對數。

           歸因（證據，非推測）：stage 0 無 replay、本卡改動的函式根本不會執行，
           該 stage 15 筆 `selected_idx` **0 筆不同**，但權重已有 1e-6 量級差；
           分歧自 stage 1 起全面出現。機制與 DR-052 記錄的 Mac/pod 分歧相同
           （浮點非結合性經 top-k 離散決策放大）。

           **PI 裁定 A**：判定為平台浮點差異，往下跑 probe。附帶紀律：
           本批與 exp3 **不同機器**、baseline 未逐位元對齊，**exp3 的數字只能當
           參考，不得與本批相減**；四個 probe run 必須同批同機（已排定）。

           實測工時留檔：**單 run 4,466 s = 74.4 分鐘**。若後續擴到二十折，
           40 run 在這台是**四波約 5 小時**，不是先前估的 2.5 小時。

           ## 補記 2026-09-18（第 7 步第一批的 run 2／run 4 作廢；側倉改為一 run 一目錄）

           第一批四個 run 中，**只讀候選的兩個（run 2 reverse、run 4 forward）作廢**。

           原因：兩者共用 `--tag cand_m128_r256`，而 `run_exp2.py` 由 tag 推導側倉
           路徑，於是兩個 run 寫進同一個目錄。側倉檔名是 `(tau, sample_key)` 的純
           函數，但**候選集合取決於快照當下的模型狀態** —— 兩個順序的模型狀態不同，
           於是互相覆寫。

           證據（mtime，非推測；單位為 epoch 秒）：

           | task | 側倉 mtime | 寫入者 | 之後仍在讀它的 run |
           |---|---|---|---|
           | tcga_rcc | 1789661805–860 | run 4 | run 2（跑到 1789661915） |
           | tcga_lung | 1789661825–898 | run 2 | run 4（跑到 1789661952） |

           側倉檔數 2,273 = 各 task train 張數總和（120+616+763+774），證實兩個 run
           共用同一組檔名。兩者都在自己的 stage 3 讀到了對方寫的候選特徵。

           **run 1／run 3（讀整張）不受影響** —— 它們從不碰側倉。

           兩處修正（commit `2cfc413`）：

           1. 側倉**一個 run 一個目錄**，目錄名就是 run 的識別字串（與 per_slide
              檔名同一個 tag，含 arm／order／seed／|M|／arch／head／uold）。
           2. 側倉檔加存 `cand_idx` 當**身分憑據**，`load_cand_features` 比對不符即
              硬失敗。這次之所以能靜默毀掉兩個 run，正是因為沒有任何東西擋得住
              「載回別人的候選」：`_candidate_terms` 的位置對齊會沉默地對到別人的
              patch。代價每筆 k×8 B（k=256 時 2 KB，約 0.4%）。

           第二批（tag 加 `_b2`）四個 run 全部重跑，掛在第一批鏈尾、不並行：四路平行
           的競爭條件一致，wall-clock 才可比；兩批的 rfull 結果應逐位元相同，正好
           當作同機決定性的免費核對。第一批的產物保留不刪，作為本補記的證據。

           ## 補記 2026-09-18（第 7 步第二批完成：**未通過**凍結判準，不進第 8 步）

           四個 run 同批同機四路平行，全部 rc=0，檔案守門與 `cand_idx` 憑據全程未觸發。

           | 順序 | 設定 | ACC | Masked ACC | Forgetting ↓ | wall-clock |
           |---|---|---|---|---|---|
           | reverse | 讀整張 | 0.7651 | 0.9124 | 0.1902 | 65.0 min |
           | reverse | 只讀候選 | 0.7299 | 0.8678 | 0.2264 | 28.5 min |
           | forward | 讀整張 | 0.8075 | 0.9071 | 0.0728 | 65.2 min |
           | forward | 只讀候選 | 0.7949 | 0.8945 | 0.1307 | 28.3 min |

           配對（只讀候選 − 讀整張）：reverse ΔACC **−3.52**、ΔMasked −4.46、
           ΔForgetting **+3.62**；forward ΔACC −1.27、ΔMasked −1.26、ΔForgetting **+5.78**。

           **判準 4/7 未過**（reverse 的 ACC／Masked／Forgetting 三條，forward 的
           Forgetting 一條）；方向一致性通過（兩序 ΔACC 同號）。依第 8 步的前提
           「僅在第 7 步結果可接受時做」，**不啟動第 8 步**（腳本已備妥）。

           同機決定性核對通過：第一批與第二批的「讀整張」per_slide **逐位元相同**
           （reverse sha256 aa27dddab141…、forward e7eb25d5669e…）。這台機器上的
           結果可重現，所以上面的差值是真實效應，不是雜訊。

           資料量（逐筆配對實測，2,273 張訓練 slide）：單一 replay 步驟側倉平均
           526,212 B vs 完整檔 6,590,862 B（**12.5×**，最大一張 44×）；**方法真正
           需要保留的 |M| = 128 筆共 64.2 MiB**，對同一批 slide 的完整特徵檔
           13.95 GiB 是 **0.45%**。哪 128 筆由無模型重放 `ReservoirSampling(seed=0)`
           算出確切集合（測試與真正的 SelectionMemory 逐筆比對），不是用平均估。
           側倉如實寫出為 1.1139 GiB／2,273 檔 —— 差距純屬實作細節（寫入早於汰換、
           汰換時未刪檔），不是方法性質。

           **結論的口徑**：降幅**不是壓縮誤差**，是換了 replay 定義的後果。寫成
           「buffer 變小、效果幾乎不變」不誠實。fold 1 單折、無變異數，本 probe 能說的
           只有「沒有崩掉，但代價可量測」。要判定這個代價可否接受，必須擴到完整十折／
           二十折，對照組與實驗組同批同機。產物：`outputs/exp4/DR056_PROBE.md`、
           `outputs/exp4/BATCH1_INVALID.md`（第一批存證）。

           ## 補記 2026-09-18（PI 裁定：**放棄候選級 replay，不做第 8 步**）

           PI 裁定放棄。理由（原文要旨）：reverse 三條判準同時未過；**Masked 掉
           4.46 pp 代表當前任務的證據品質也下降**，不只是舊任務的記憶；兩序
           Forgetting 都明顯升高，正好落在老師最關注的指標上。**自足性只有在成績
           站得住時才有價值** —— 所以第 8 步不做。

           處置：分支 `exp/candidate-replay` 與 `outputs/exp4/`、`logs/exp4/` 全部
           **保留、不刪除、不 merge 回 main**。論文會引用這批數字作為設計選擇的依據，
           口徑見 `docs/RESULTS_DOSSIER.md` §11.11。

           本卡的 ruling（走磁碟側倉、group 蒸餾用 g_stored、CONTRACT-3 加欄）在
           **探針的範圍內**仍然成立且已實作驗證；但該設計**不進主線**。main 的
           CONTRACT-3 不受影響：`group_prototypes` 預設 `None`，且整個候選級路徑只在
           `replay.candidate_only: true` 時啟用，主線組態未改。

           一句話結論：**候選級 replay 可行（12.5× 少讀、buffer 0.45%、每 run 快
           36 分鐘），但代價可量測（ACC −1.3～−3.5 pp、Forgetting +3.6～+5.8 pp），
           本版不採用。**
