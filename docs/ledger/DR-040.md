# DR-040  G4 必須自己接上 q_tau —— run_exp2 一律餵零向量
date: 2026-08-24    status: ACTIVE
context:   準備 G4 時查證 `run_exp2.Ctx`，發現 `self.q0 = torch.zeros(512)`，
           所有實驗一律把這個**零向量**當 q_tau 傳給 train_step / run_rounds。
           而 `use_query=False` 的實作是把 query 欄位**填零而不縮短維度**
           （selector/model.py:44）。兩者相加的後果：只把 `use_query=True` 打開、
           不接真正的 q_tau，selector 的輸入與關閉時**完全一樣**。
           實測（20 組 synthetic、hier、per_budget）：
             q_tau = zeros(512) → 選取集合與 use_query=False 相同 **20/20**（位元相同）
             q_tau = 真 task query → 相同 16/20（4 組不同）
           即 G4 若照原樣跑，會是**由構造保證的 null**（憲法 §2.5），
           而不是「q_tau 沒有用」這個科學結論。
options:   (a) 照原樣跑 G4，得到必然的 null
           (b) 接上 TaskQueryBank，讓 q_tau 真的帶任務身分再測
           (c) 停下來問 PI
           ※ 本行由 Cursor 補上，PI 未原文指定選項清單
ruling:    (b)。PI 對 G4 的原文是「q_tau 進 F_g 與 F_p，定義依 DR-008 凍結版本不變」——
           零向量不是 q_tau，接上 TaskQueryBank 是執行該指示，不是改變它。
           接線由 `run_arch_completeness.wire_task_queries` 以 runtime injection 完成，
           四個注入點：train_stage / evaluate（該 task 的 q_tau）、fill_memory（寫入
           時用該 task 的 q_tau）、continual_terms（用 **entry.tau** 的 q_tau ——
           舊樣本屬於它自己的 task，不是當前 task）。
           PI 要求的 leakage 閘門（同 task 位元相同、跨 task 不同）在 G4 啟動時
           以 `check_query_leakage` 實際執行，不只是單元測試。

           **既有結果不受影響**：`run_exp1.py` 走的是 `encode_task_query`（真 query），
           Exp 1 的 L4 vs L3 有效；`run_exp2.py` 雖然餵零向量，但從未開啟 use_query，
           零向量從未進入任何已發表的數字。**沒有結果需要撤回。**
