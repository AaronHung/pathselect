# 專案憲法 — 不隨單次實驗改動的規則

這裡放**跨實驗、跨報告都適用**的政策。單次裁定寫在 `ledger/DR-0xx.md`；
會反覆套用的規則升格到這裡，並在對應的 DR 卡留下來源。

> 入口順序：`ledger/INDEX.md` → 本檔 → status=ACTIVE 的 DR 卡。

---

## §1 統計政策

### §1.1 三級 win count 規則（來源 [DR-020](ledger/DR-020.md)）

臂間比較一律**配對**（同 seed 相減）。win count 的判讀只有三級，全文統一用詞：

| win count | 名稱 | 判讀 |
|---|---|---|
| 5/5 | **systematic** | 系統性差異 |
| 4/5 | **directional, inconclusive** | 方向一致但證據不足以定案 |
| ≤3/5 | **within noise** | 落在雜訊內 |

### §1.2 n < 5 的批次（來源 [DR-023](ledger/DR-023.md)）

**三級規則是為 n = 5 校準的。** n < 5 的批次一律加註：

> 本批的 systematic 應讀作**方向一致**而非**已定案**；
> 寫進論文的主張必須回到 5-seed 的批次確認。

報告產生器（`scripts/run_exp2.py::write_paired`）在 `len(seeds) < 5` 時**自動加註**，
不依賴人工記得。

### §1.3 跨批次配對（來源 [DR-024](ledger/DR-024.md)）

兩個批次的 seed 數不同時，跨批次配對**只能用共同子集**，但該子集**不必代表母體**。
任何跨批次宣稱必須同時檢查：

- **(a)** 共同子集的配對結果
- **(b)** 該對照在**各自批次的全 seeds** 上是否成立

**兩者不一致時以 (b) 為準**，並在報告中揭露差異。

> 證據鉤子：`A2 − A1` 在 reverse 的**全 5 seeds** 為 **−3.09 pp（3/5, within noise）**，
> 但共同 seeds 0–2 為 **+7.92 pp**；逐 seed 幅度橫跨 43 pp
> （`+1.84, +16.31, +5.61, −11.91, −27.29`）。僅看共同子集會得出「LoRA merge 有
> 順序效應」的錯誤結論。

> **第二個實例（H1，2026-08-25）**：`B2 − A5` 的 class-IL 在 3 seeds 下為
> **+3 個全正**（看起來 B2 勝出），補到 5 seeds 後逐 seed 為
> `+2.25, +0.51, +0.62, −2.56, −8.27`，配對 **−1.49 pp（3/5, within noise）**。
> **前三個正好就是 3-seed 批次的 seeds 0–2。** 同一個陷阱在兩週內出現兩次，
> 這不是巧合 —— 小樣本子集的方向一致性極易誤導。

### §1.4 不報 p 值（來源 [DR-016](ledger/DR-016.md)）

n = 5 的樣本數下顯著性檢定會誤導。一律報逐 seed 配對差值、配對 mean ± std
與 win count。

### §1.5 效果量的最小可辨識度

esca 只有 15 張 test slide，**一張 = 6.67 pp**。esca 上小於該值的差異一律標註為
**不可區分**，不得用來支撐任何主張。

## §2 證據政策

### §2.1 逐 slide 存檔（來源 [DR-012](ledger/DR-012.md)、裁定 C）

`outputs/` 下每一次評估都必須落一份逐 slide JSON
（`slide_id` / `task` / `true` / `pred*` / 選取類另加 `selected_idx` / `weights`）。
由 `tests/test_per_slide_records.py` 把關。理由：v9 只存彙總 accuracy，
導致 flip 分析只能給區間。

### §2.2 科學主張要 mutation check（來源 `tests/README.md` §1b）

要宣稱「某模組有作用 / 無作用」時，優先用**替換或擾動實測**，不要只讀 code 推論；
並且必須做反向對照，否則分不清「模組沒作用」與「替換沒生效」。

### §2.3 斷言要 mutation check（來源 `tests/README.md` §1）

2026-08-24 之後新增的每條 assert，提交前必須以人工製造的違例確認它會失敗。
提交訊息以一行註明違例內容。

### §2.4 撤回程序（來源 [DR-024](ledger/DR-024.md)）

發現先前回報的結論有誤時：**主動撤回、說明查證方式、並附方法學教訓。**

**撤回不算失分，隱瞞才算。** 尤其當 PI 已根據該錯誤下達過指示時，
撤回是唯一能讓後續決策站在正確基礎上的做法。

撤回應包含三件事：

1. 明確指出哪一句話是錯的、錯在哪裡；
2. 查證方式（跑了什麼、看了什麼數字）；
3. 一條可以防止同類錯誤再發生的規則 —— 若該規則會反覆適用，升格進本憲法。

> 證據鉤子：`A2 − A1` 順序效應的撤回（2026-08-25）。該錯誤已進入 PI 的
> H-SERIES 指示中，撤回後改列為 seed 變異，並衍生本檔 §1.3。

### §2.7 字串替換必須斷言錨點（來源 [DR-027](ledger/DR-027.md)）

以字串替換修改檔案時：

1. **替換前**斷言錨點存在，且出現次數符合預期；
2. **替換後**斷言結果包含新內容。

**錨點不存在時必須失敗，不得靜默通過。**

> 證據鉤子（同類錯誤兩週內第二次）：
> - 2026-08-24：兩處替換未命中卻通過，導致報告用詞未統一。
> - 2026-08-25：`run_exp2.py` 的**模組層 import 錨點根本不存在**
>   （`run_rounds` 是在函式內 import 的），`replace` 靜默失敗，
>   只加了 `--allocation` 的用法沒加 import。**671 條測試全綠**，
>   因為 `import` 模組不會執行 `main()`；直到排隊中的 job 撞上去才爆炸，
>   而 G1' 因此整批被靜默跳過。

配套：`tests/test_cli_entrypoints.py` 用 `--help` 走完 argparse 設定，
補上 import 測試抓不到的那一層。

### §2.8 回報內容必須存在於 committed 產物中（來源 [DR-030](ledger/DR-030.md)）

**任何寫進回報的表格或數字，必須同時存在於 committed 的產物檔中。**

- 回報前確認該檔確實含該內容（`grep` 一下就好）；
- 臨時以 python 算出的數字**必須先寫進產物再回報**，不得只出現在對話裡。

> 證據鉤子：2026-08-23 的 G1 回報貼出結構性診斷表（84.5% 單組），數字有效且可重算，
> 但因 `replace` 錨點失效而**從未寫入 `HIER.md`**。PI 據此下達過裁定，
> 而那張表在 repo 裡找不到。對話會消失，產物不會 —— 兩者不一致等於沒有證據。

### §2.5 隔離前先檢查退化（來源 [DR-025](ledger/DR-025.md)）

「一次只動一個變因」在變因**結構耦合**時會製造退化組態。

**隔離某一機制之前，必須先檢查：關閉另一個變因後，該機制是否仍有作用空間。**

> 證據鉤子：G1 在 `c=1` + `state off` 下，階層配額退化為單組選取
> （84.5% 的 slide 只用一組）。「只開階層、不開 state」在方法上正確，
> 但 per-chunk 配額 + c=1 + r 逐輪不變三者相乘的結果是「階層」根本沒有作用空間。

檢查方式：**先跑結構性指標**（例如「每張 slide 用到幾個 group」），
確認機制真的在動，再花算力跑完整實驗。結構性檢查只需幾分鐘。

### §2.6 機制宣稱前先驗證非 no-op（來源 [DR-025](ledger/DR-025.md)）

宣稱某個結構（sequential loop、階層、狀態條件化）有作用之前，
必須先證明**關掉它會改變輸出**。

> 證據鉤子：`use_state=False` 時 c=1 八輪與 c=8 一輪的選取**位元相同**（20/20），
> 亦即所有已跑實驗的 chunked loop 在資訊上是 no-op。
> 不可宣稱的清單維護在 [CLAIMS.md](CLAIMS.md)。

## §3 報告政策

### §3.1 forgetting 類指標只算前 T−1 個 task

最後學的 task 兩個時點是同一個，A1 恆為 0、Jaccard 恆為 1，算進去會稀釋量級。
final average accuracy 與洩漏率仍算全部 T 個。

### §3.2 負面結果照實報

方法沒贏 baseline、順序依賴、中段證據弱 —— 一律獨立成節寫明，不美化、
不調參數搶救。這是 [DR-015](ledger/DR-015.md) 與 [DR-019](ledger/DR-019.md) 的共同要求。

### §3.3 參照臂不是 baseline

per-task specialist（獨立訓練）與 joint offline 的 forgetting 由構造為 0，
不得用來宣稱 forgetting（[DR-011](ledger/DR-011.md)）。

### §3.4 執行期檔案凍結（來源 [DR-026](ledger/DR-026.md)）

**有 job 在跑時，不得編輯該 job 會呼叫的任何檔案。**

必要時兩種做法：

- **(a)** 等 job 結束再改；或
- **(b)** 把要改的腳本複製到凍結路徑（`scripts/_frozen/<job>_<日期>.py`），
  讓跑中的 job 呼叫凍結副本，在原檔上編輯。

每個長 job 啟動時，把它所呼叫檔案的 git commit hash 記到 log 開頭，結束時再記一次；
兩者不同即在報告中標為 **「執行期檔案曾變動」**。

> 證據鉤子：2026-08-25 編輯 `run_exp2.py` 時，排隊中的 job 正要呼叫它，
> 抓到改到一半的版本 → `NameError: ALLOCATION_MODES`。**G1' 因此整批被靜默跳過**
> （shell 沒檢查 exit code，卻印出「完成」）。
>
> 這次因語法錯誤而大聲失敗；**若該次編輯語法正確但語意不同**（例如改了
> `allocation` 預設值），排隊的 job 會**靜默地用新行為跑出結果**，而我們無從察覺。

### §3.6 報告腳本的最小資料煙霧測試（來源 [DR-028](ledger/DR-028.md)）

**每個報告腳本必須有一條測試，用最小的真實或 fixture 資料實際跑完 `main()`**，
斷言產出非空且含預期章節標題。

**批次腳本在宣告完成前，必須先成功執行其報告腳本。**

> 證據鉤子：同類錯誤三次，前兩層防護都擋不住第三次 ——
> - `import` 測試擋不住 `main()` 內的錯（不執行 main）；
> - `--help` 測試走完 argparse，但擋不住需要**真實資料**才觸發的錯。
> - 2026-08-23 `ALLOCATION_MODES`（argparse 期，`--help` 抓得到）；
>   同日 `diag`（需要資料才觸發，`--help` 抓不到）。
>
> 更嚴重的是：`report_hier.py` 的結構性診斷區塊**從未真正寫進腳本**
> （錨點在更早的編輯後已不存在，`replace` 靜默失敗），因此 `HIER.md` 一直沒有
> 那一節，而我卻在回報中貼出了該表 —— 數字是另一段獨立 python 算出來的、有效，
> 但**報告與回報不一致**。這正是 §2.7 與本條要一起防的。

### §3.7 長 job 必須有存活訊號（來源 [DR-032](ledger/DR-032.md)）

**每個長 job 每完成一個階段就在 log 追加一行帶時間戳的心跳：**

```
[heartbeat] <ISO時間> stage=<n/N> <描述>
```

**非零結束時**，在 log 最後追加 `[FAILED] <階段> <錯誤摘要>`，並另外寫一份
`outputs/_status/<job>.json` 記錄 `{state, stage, note, updated_at, started_at}`。

這樣只要看一個檔就知道 job 是**活著、完成、還是死了**。
實作見 `scripts/job_status.py`；`trap ... ERR` 負責失敗路徑。

> 證據鉤子：2026-08-23 的 pipeline **在第一行就死**，log 只有一行錯誤，
> 沒有任何完成或失敗標記，是 PI 手動看 log 才發現。

#### 附帶：狀態檔要主動讀，不是寫了就算

§3.7 的狀態檔在 2026-08-24 正確標記了 `failed`，但**沒有人讀它**，
pipeline 死了 6 小時無人察覺。

> **每次回報前，先讀 `outputs/_status/*.json`，並在回報開頭一行說明所有 job 的
> 當前狀態。** 這是零成本的，但它是唯一能讓自己發現 job 死掉的機制。

#### 附帶：zsh 不對未加引號的變數做 word splitting

`R="python foo.py"; $R` 在 **bash 會展開成兩個詞、在 zsh 會被當成一個檔名**。
批次腳本**不得用變數當命令**，每一行都要是完整可執行的命令。
這正是上述 pipeline 第一行就死的直接原因（不是相對路徑問題 —— `cd` 有生效）。

### §3.6b 報告腳本的 fixture 必須涵蓋所有遍歷維度（來源 [DR-034](ledger/DR-034.md)）

§3.6 要求「用最小資料跑完 main()」，但**最小資料若只涵蓋單一維度，
出錯的那行根本不可達**。

> **報告腳本的測試 fixture 必須涵蓋該腳本實際會遍歷的所有維度**
> （order / arch / prior / arm / 記憶體容量 / seed 數不齊 等）。
> 只用單一維度的 fixture 不算通過。
> 新增測試前先確認：拿掉被測的那個 key，測試是否會紅（mutation check）。

> 證據鉤子：同類錯誤第四次。`report_order_dependence.py` 的
> `KeyError: 'final_task_il'` 只在「兩個 order 且各 arm 的 seed 數不齊」時才會踩到 ——
> 單 order fixture 下不可達，§3.6 的測試全綠卻擋不住。

#### 附帶：跨 tag 蒐集必須過濾**所有**識別維度

同日另一個更危險的例子：`report_prior.py` 跨 tag 蒐集時只過濾了 `arch`，
沒過濾 `allocation`，於是把 **G1 的退化紀錄**（per_chunk，階層 88.6% 單組）
當成 discriminative 主線臂，產出「主線遠差於 none / max_sim 共 −17.5 pp」的
**假結論**。修正後三臂實際上都在雜訊內。
**跨 tag / 跨批次蒐集時，每一個會改變語意的欄位都必須明確過濾，缺欄位一律視為舊語意。**

### §3.5 批次腳本的失敗語意（來源 [DR-027](ledger/DR-027.md)）

**1. 所有批次腳本必須 `set -euo pipefail`。**

**2. 「完成」訊息只能在該批次的產物通過存在性檢查之後印出**，
不得只因為執行流程走到最後一行就宣告完成。

**3. 每個批次結束時檢查預期產物數量**（例如 `per_slide` 檔數 = arms × seeds），
數量不符即以**非零狀態**結束，並在 log 明確標示缺了什麼。

> 證據鉤子：`g1prime.sh` 沒有 `set -e`，`run_exp2.py` crash 後照樣往下走並印出
> 「=== G1' 完成 ===」。**G1' 整批未執行**（`hier2/per_slide` 為 0 份），
> 但 log 看起來是成功的。**這比 crash 本身危險** —— crash 會被看見，
> 偽裝成成功的失敗不會。
